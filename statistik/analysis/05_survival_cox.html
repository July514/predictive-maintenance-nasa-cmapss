1. Modell A: Cox mit statischen Covariaten

Als direkten Vergleich zu Weibull AFT starten wir mit demselben Ansatz: eine Zeile pro Engine, Mittelwert der letzten 20 Zyklen als statisches Sensor-Feature.

Das erlaubt einen sauberen methodischen Vergleich: gleiche Prädiktoren, gleiche Datenstruktur — Weibull (parametrisch) vs. Cox (semi-parametrisch).

Code 
# Eine Zeile pro Engine: Lebensdauer + letzte 20 Zyklen gemittelt
lifetimes_static <- train %>%
  group_by(unit_number) %>%
  summarise(
    lifetime = max(time_in_cycles),
    event    = 1L,
    across(all_of(cox_sensors),
           ~mean(tail(.x, 20)),
           .names = "{.col}")
  ) %>%
  ungroup()

2. Modell B: Cox mit zeitabhängigen Covariaten

Der methodische Kernvorteil von Cox gegenüber Weibull AFT: zeitabhängige Covariaten. Statt dem Mittelwert der letzten 20 Zyklen nutzen wir den tatsächlichen Sensorwert zum jeweiligen Zeitpunkt — die vollständige Zeitreihe.

Dafür brauchen wir das Counting-Process-Format (start, stop, event): jede Zeile beschreibt ein Zeitintervall. event = 1 nur in der letzten Zeile der Engine (Ausfall), alle anderen Zeilen haben event = 0.

Code 
# Counting-Process-Format: (start, stop, event) pro Zeitschritt
# start = t-1, stop = t, event = 1 nur beim letzten Zyklus

cox_long <- train %>%
  select(unit_number, time_in_cycles, all_of(cox_sensors)) %>%
  group_by(unit_number) %>%
  mutate(
    max_cycle = max(time_in_cycles),
    start     = time_in_cycles - 1,
    stop      = time_in_cycles,
    event     = if_else(time_in_cycles == max_cycle, 1L, 0L)
  ) %>%
  ungroup() %>%
  filter(start >= 0) %>%
  select(unit_number, start, stop, event, all_of(cox_sensors))

# Zusammenfassung PH-Test: welche Prädiktoren sind betroffen?
ph_summary <- function(zph_obj, modell_name) {
  df <- as.data.frame(zph_obj$table) %>%
    rownames_to_column("predictor") %>%
    mutate(
      Modell     = modell_name,
      ph_verletzt = if_else(p < 0.05, "ja — PH verletzt", "nein — PH hält")
    ) %>%
    select(Modell, predictor, chisq, df, p, ph_verletzt)
  df
}

4. Umgang mit PH-Verletzungen: Stratifizierung

Wenn ein Prädiktor die PH-Annahme verletzt, gibt es eine saubere Lösung innerhalb von Cox PH: Stratifizierung.

Wir teilen die Engines in die zwei Fault-Mode-Gruppen (kurze vs. lange Lebensdauer, identisch zu KM-Analyse) und schätzen für jede Gruppe eine eigene Baseline-Hazard. Die Koeffizienten der verbleibenden Prädiktoren werden weiter geteilt geschätzt.

Code 
# Fault-Gruppe zuweisen (identisch zu KM-Analyse)
cox_long_strat <- cox_long %>%
  left_join(
    train %>%
      group_by(unit_number) %>%
      summarise(lifetime = max(time_in_cycles)) %>%
      mutate(fault_group = if_else(lifetime < 300, "kurz", "lang")) %>%
      select(unit_number, fault_group),
    by = "unit_number"
  )

# Stratifiziertes Cox-Modell: strata(fault_group) bekommt eigene Baseline-Hazard
cox_strat <- coxph(
  Surv(start, stop, event) ~ sensor_11 + sensor_17 + sensor_3 + sensor_2 +
                             strata(fault_group),
  data    = cox_long_strat,
  ties    = "efron",
  cluster = unit_number
)

Methodische Einschränkungen

  • Counting-Process und Cluster-SE: Die Cluster-robusten Standardfehler korrigieren für Within-Engine-Korrelation, lösen aber keine echte Abhängigkeitsstruktur. Gemischte Effekt-Modelle (Frailty-Modelle) wären präziser, übersteigen aber den Kursrahmen.

  • Nur 4 Prädiktoren: Die Sensor-Auswahl basiert auf Korrelation und VIF aus der EDA. Ein penalisiertes Cox-Modell (ridge/lasso via glmnet) würde alle 12 finalen Sensoren einbinden und automatisch selektieren — sinnvoll als Erweiterung.

  • Keine Kreuzvalidierung: Der Concordance-Index wurde auf den Trainingsdaten berechnet (In-Sample). Für einen echten Vergleich mit ML-Modellen wäre Leave-One-Out-CV oder k-Fold auf Engines nötig.

  • Abschluss des Statistik-Teils: Dieses Notebook schließt die drei Survival- Analyse-Methoden ab. Der ML-Teil (ml/notebooks/) nutzt dieselben Sensoren und denselben Datensatz, modelliert aber RUL direkt als Regressionsproblem ohne Verteilungsannahmen.
